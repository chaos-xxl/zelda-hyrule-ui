# 排版能力集成方案：塞尔达视觉 × 归藏排版（路径 A · 互操作适配层）

> 把 zelda-hyrule-ui 的「塞尔达视觉皮肤」与归藏（op7418）两个排版 skill 的「专业排版骨架」结合，让用户用 AI 生成 PPT / 网页 / 配图时，既有塞尔达风格、又有专业排版。
>
> 本文档为执行前的固化方案。确认后据此动手。**核心决策：走「互操作」而非「合并代码」，以规避 AGPL 传染、保住本项目 MIT 定位。**

> **想法成立、互补性强、技术可行。唯一要绕开的是 AGPL 许可证传染——绕法是「互操作」（各装各的 skill + 我们只提供桥接说明），而不是「fork 合并代码」。**

## 1. 背景：我们到底缺什么

### 1.1 问题来源

在为项目做小红书宣传配图时发现：我们能做出排版不错的图，但靠的是**手动借用**归藏的瑞士排版逻辑（网格、字号对比、发丝线、大数字），而不是 skill 里有现成规范。这暴露出一个真实缺口。

### 1.2 三层「排版」的区分（关键认知）

「排版」是个被混用的词，必须拆成三层看：

| 层 | 回答的问题 | 我们现在有吗 |
|---|---|---|
| **视觉风格** | 一个元素长什么样（色 / 辉光 / 边框 / 字体 / 组件） | ✅ 定义得很细（design-tokens、core-patterns、83 个组件） |
| **游戏 UI 布局** | 怎么排一个 HUD / 库存格 / 对话框 | ✅ 有（recipes 9 个场景 + ui-cases 5 个游戏界面） |
| **信息排版** | 怎么把一个观点 / 一组数据 / 一篇文章排成好看的 PPT 页、海报、落地页 | ❌ **完全没有** |

**结论：我们有「视觉皮肤」和「游戏界面布局」，但完全缺「信息排版系统」。** 这正是归藏两个 skill 的核心能力。

## 3. 为什么两者天然互补（正交的两层）

它们管的是**正交**的两件事，可以「骨 + 皮」组合：

```
        ┌─────────────────────────────────────┐
        │  归藏 skill = 排版引擎（骨架）          │
        │  怎么在页面上组织信息：               │
        │  网格 / 版式 / 字号层级 / 留白 / 节奏   │
        │  （它甚至刻意禁止自定义颜色——          │
        │    因为它管结构，不管皮肤）            │
        └─────────────────────────────────────┘
                         +
        ┌─────────────────────────────────────┐
        │  zelda-hyrule-ui = 视觉皮肤（皮）      │
        │  长什么样：                          │
        │  希卡蓝 / 辉光 / 扫描线 / Hylia 字体 / │
        │  双层边框 / 83 个塞尔达组件            │

        「归藏版式骨架 + 塞尔达视觉皮肤」
```

**最有力的可行性证据**：本项目已上线的 8 张小红书配图（`#/xhs` 页面）就是「骨 + 皮」的雏形——用归藏的瑞士排版逻辑 + 塞尔达希卡视觉手搓出来的，已证明组合在视觉上成立。本方案要做的，就是把这个"手搓过程"沉淀成 skill 里可复用的规范。

## 4. 核心约束：AGPL 许可证（决定怎么做）

### 4.1 许可证冲突

| 项目 | License | 性质 |
|------|---------|------|
| 归藏两个 skill | **AGPL-3.0** | 最强传染性 copyleft |
| zelda-hyrule-ui | **MIT** | 极宽松 |

### 4.2 单向兼容机制

```
MIT 代码  ──可以流入──>  AGPL 项目   ✅
AGPL 代码 ──不能流入──>  MIT 项目    ❌
```

- MIT 代码可被吸进 AGPL 作品（合法）
- 反过来不行：**不能把归藏 AGPL 代码拿来贴 MIT 标签再分发**
- 一旦把它的模板 / 版式代码 merge 进我们仓库去改，那个「合并成品」就**被 AGPL 锁死**——必须整体 AGPL 开源、连部署成网络服务也要给源码

### 4.3 为什么"转 AGPL"对组件库是自杀

AGPL 的传染性让"用了它的整个产品都得开源"。对一个**靠被广泛 import 才有价值**的 UI 组件库：

| 谁想用 | 用了 AGPL 会怎样 | 结果 |
|--------|----------------|------|
| 公司闭源产品 | 整个 App 源码都得公开 | 法务直接拉黑 |
| 创业 SaaS | 即使不分发代码，上线给用户用也要公开源码 | 不可接受 |
| 接私活开发者 | 交付的项目要开源 | 没法交付 |
| 个人 / 学习 | 自己玩不分发 | ✅ 没事，但不带来传播 |

**真正推动组件库火起来的人（公司、创业者、接活者）全被挡在门外。** AGPL 适合"想防着别人白嫖"的服务端项目（数据库、SaaS 后端），不适合"想让所有人都来用"的前端组件库。

### 4.4 许可证变更的事实澄清（备查）

- **同一项目可以变更 license**，前提是版权持有者同意（本项目基本是独立开发，无外部贡献者障碍）。
- **变更不可追溯**：已发布的 MIT 旧版本（如 v0.1.1）永久是 MIT，已 fork / 已安装的用户不受影响。只有"变更后发布的新版本"受新 license 约束。
- 但**没必要也不应该**为了集成排版能力去转 AGPL——见 4.3。

## 6. 路径 A 详细设计

### 6.1 核心理念

我们**不碰归藏的代码**。我们只新增一份**原创的桥接文档**，告诉执行 Agent：

> "当用户想要『塞尔达风格 + 专业排版』时，配合用户已安装的归藏 skill 产出版式骨架，然后用本文档的 token 覆盖规则，把视觉皮肤换成塞尔达。"

桥接文档是我们 100% 原创的内容（覆盖规则、token 映射、使用流程），不复制归藏任何代码 / 模板 / 版式定义，因此 AGPL 传染不过来，本项目稳留 MIT。

### 6.2 适用边界（诚实声明）

- ✅ 适用：归藏的 **Style B 瑞士风**（纯结构 + 单锚点色，最适合换皮）
- ⚠️ 部分适用：电子杂志风（依赖特定字体 / 纸纹，换皮后会失真，不主推）
- ❌ 不处理：归藏的 WebGL 墨流背景、图源工作流（与塞尔达视觉无关，保持原样即可）

### 6.3 Token 覆盖映射（桥接文档核心内容）

把归藏瑞士风的设计变量，一一映射到塞尔达 token：

| 归藏瑞士风 | 默认值（如 IKB） | 覆盖为塞尔达 | 来源 token |
|-----------|----------------|-------------|-----------|
| 锚点色 anchor | `#002FA7` | 希卡蓝 `#3CD3FC` | `@sheikah-blue` |
| 背景 | 白 / 浅 | 深色 `#66645D` 或 `rgba(10,20,40,0.9)` | `@zelda-dark-bg` |
| 正文文字 | 近黑 | 暖白 `#E9E1D1` | `@text-color-main` |
| 标题字体 | Inter / Helvetica | Hylia Serif | `@font-title` |
| 正文字体 | Inter | Roboto italic | `@font-body` |
| 发丝线 | 1px 纯色 | 1px `rgba(60,211,252,0.16)` | 希卡蓝低透明 |
| 强调 / 选中 | 锚点色块 | 希卡蓝 + 辉光 `@glow-sheikah` | 辉光系统 |
| 装饰层 | 无 | 叠 `SheikahScanlines` 扫描线 | 组件 |

> 注：上表右侧 token 全部来自我们自己的 `references/design-tokens.md`，是原创映射，不含归藏任何数据。

### 6.4 保留归藏的"硬规则"（不冲突，直接沿用）

这些是排版结构规则，与视觉皮肤无关，应明确告诉 Agent 继续遵守：

- 网格锁定（16 列）、版式从具名骨架里选不要自创
- "越大越细"（大标题降字重）
- 中文大标题降一档
- 图文底对齐、图片进预留槽位
- 单锚点色（我们的锚点色 = 希卡蓝，不要再引入第二个高饱和色）

## 10. 远期路径 C：自建塞尔达排版系统（暂不做，观察后再定）

> **定位：C 不是 A 的替代，是 A 的「毕业版」。** A 借归藏的引擎跑通流程；C 是我们自己造一台引擎——在自己的 skill 里内建一套原创的「塞尔达信息排版系统」，不依赖任何外部 skill，全程保持 MIT。
>
> **当前状态：不启动。** 本节是"随时能启动的清单"，等触发信号出现再照此执行。

### 10.1 C 是什么

把现在 `#/xhs`、`#/poster` 里"手搓"的版式，升级成一套**可复用、可参数化、Agent 能直接调用的版式骨架库**——相当于自己做一个迷你版"归藏排版"，但皮肤天生是塞尔达的。

### 10.2 License 红线（最关键，先讲）

C 和"抄归藏"是两回事，靠这条边界区分：

- ✅ **设计原则不受版权保护**：瑞士国际主义、网格系统、字号层级、留白节奏是公共设计知识，归藏不拥有，任何人可用。
- ❌ **具体表达受保护**：归藏写的那段具体 HTML/CSS、版式命名（S01–S22）、模板代码——不能照抄。
- **铁律：开发 C 时不许打开归藏的模板文件**，只凭设计原则 + 我们自己的 `#/xhs` / `#/poster` 成品来写。学知识，不抄代码。

> 类比：可以学"瑞士设计要用网格 + 单锚点色"这个道理，但不能复制别人写好的网格 CSS。前者是知识，后者是表达。

### 10.3 产物（全部原创）

**(1) 版式骨架 reference**（如 `references/layout-system.md`）——初期只固化最高频的 6 个具名版式，**这 6 个在 `#/xhs` / `#/poster` 已全部做出来，C 第一步是"抽象成规范"而非从零发明**：

| 版式名 | 用途 | 现成雏形 |
|--------|------|---------|
| `cover` 封面 | 大标题 + 副标题 + 希卡符号 | `#/xhs` 卡1、`#/poster` 1:1 |
| `kpi` 数据大字报 | 巨数字 + 说明 | `#/xhs` 卡2 |
| `feature-list` 编号特性列表 | 发丝线分隔的 01/02/03 | `#/xhs` 卡3、`#/poster` 3:4 |
| `compare` 对比页 | before/after 双栏 | `#/xhs` 卡6 |
| `grid` 分类网格 | 数字 + 标签矩阵 | `#/xhs` 卡7 |
| `cta` 收尾页 | 代码块 + 链接引导 | `#/xhs` 卡4、卡8 |

**(2) 画板尺寸预设**：PPT 16:9、小红书 3:4、公众号 21:9 / 1:1、海报——固定比例，原创实现。

**(3)（可选，最重）原创 HTML 模板 + 导出流水线**：把现有 `scripts/export-posters.mjs`（Playwright 3x 导出）升级成"读内容 JSON → 套版式 → 出图"的小流水线。可做可不做。

### 10.4 A vs C 得失

| 维度 | A（互操作） | C（自建） |
|------|------------|----------|
| 用户要装别的 skill | 要装归藏 | **不用，开箱即用** |
| license | 干净 | 干净 |
| 排版专业度 | 高（归藏 22 个版式成熟） | 初期低（6 个），但够用 |
| 我们的控制力 | 低（归藏更新被动跟） | **完全自主** |
| 工作量 | 已完成 | 中–大 |
| 长期价值 | 依赖外部 | **自包含，是真正的产品壁垒** |

核心权衡：**A 是"借力"，快但依赖别人；C 是"自立"，慢但属于自己。**

### 10.5 启动触发条件（满足任意一条再做）

C 应被**数据/事件触发**，而非拍脑袋启动：

1. **高频验证**：A 跑一段时间后，确认"塞尔达风排版"是用户真实高频需求（不是自嗨），值得投入做重。
2. **依赖痛点**：归藏 skill 更新 / 改 license / 停止维护，或"要求用户先装另一个 AGPL skill"本身成了门槛、劝退用户。
